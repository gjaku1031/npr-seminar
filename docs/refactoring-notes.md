# 코드 정리 기록

기존 기능을 유지하면서 정책의 기준과 HTTP·업무 처리·데이터 조회의 책임을 읽기 쉽게 정리한 기록. 실제 구현·검증 시점은 2026-09-26 이후이며 커밋의 author date 배치와 구분. 운영 배포·성능 개선 실적으로 해석하지 않음.

## 문자 편집 정책

### 문제

문자 화면의 용도별 변수 버튼과 서버의 허용 변수 검증이 각각 고정 목록을 관리하는 구조. 한쪽만 수정하면 화면에서 넣을 수 있는 변수를 저장 시 서버가 거절할 수 있음.

### 변경

`apps/api/src/modules/sms/sms-template-policy.ts`가 기존 6개 서버 용도의 변수 집합과 편집 화면에 필요한 정보를 정의. 렌더러·DTO와 관리자 정책 조회가 같은 선언을 사용. 기존 허용 변수와 FIRST_CHECK_IN의 서버 처리 범위 유지.

`GET /api/v1/admin/sms/template-policy`는 ADMIN에게 기본 용도와 편집 가능한 5개 용도의 `purpose`, `label`, `variables`, `keyPrefix`를 반환. DB 조회와 문자 발송 없음. Controller는 인증된 HTTP 진입점, Service는 정책 조회, 렌더러는 저장·발송 시 변수 검증 책임.

브라우저는 응답으로 용도 선택지·라벨·변수 버튼·신규 템플릿 키 접두어 구성. 응답을 읽지 못하면 고정 목록으로 대신 진행하지 않고 해당 편집 동작을 잠근 뒤 재시도 안내. 입력·커서·로컬 예시 문구 등 화면 표현은 브라우저에서 유지.

기존 테스트가 직접 import하는 `entities/sms/model/template-purpose.ts`는 호환 목적으로 보존하며 제품 런타임 참조는 제거. 저장소 전체의 고정 목록을 모두 삭제한 변경은 아님. HTTP 계약의 용도 타입과 응답 구조 검사는 프론트에도 존재하며 실제 용도별 허용 변수는 서버 응답 사용.

### 검증

API 타입검사·빌드, Web 타입검사·린트·정적 빌드, OpenAPI 검증 통과. Web의 기존 생성 타입이 삭제된 동적 예약 경로를 참조했던 최초 검사는 실패했으나 정적 빌드로 생성물을 갱신한 뒤 통과. 새 조회 훅의 린트 지적은 수정 후 재확인.

격리 PostgreSQL 18·Redis 7.4·Nest와 합성 데이터에서 다음을 확인. 외부 SMS·학생 원천·Google Sheets와 worker 비활성화.

| 항목 | 결과 |
| --- | --- |
| 기존 `10cd5b7` 변수 정의 비교 | 6용도의 허용 변수와 순서 동일 |
| 직접 렌더러 확인 | 허용 변수 34개 성공, 용도 외 변수 14개 거절 |
| 정책 조회 권한 | ADMIN 200, 익명 401, 실제 페어링한 SCANNER 403 |
| 템플릿 API | 잘못된 변수 400, 생성 201·수정 200·재조회 저장값 일치 |

실제 정적 프론트에서 예약 취소의 변수 칩 6개(인증번호·QR 제외), 변수 삽입 후 입력 초점 유지, 저장 후 재진입 시 본문 반영 확인. 브라우저 요청 차단으로 첫 정책 조회 실패를 모의 주입하여 편집 잠금·오류 안내·재시도 버튼을 확인하고, 차단 해제 후 편집 복구 확인. 이 장애는 실제 운영 장애가 아닌 검증 조건.

테스트 코드·테스트 스위트는 변경하거나 실행하지 않음. 운영 배포·실제 문자 발송 결과 아님. 리뷰에서 발견한 기존 템플릿 생성 재시도 문제는 아래 후속 수정으로 분리.


## 생성 응답 유실 후 재시도

기존 생성 훅은 결과가 불확실하면 Idempotency-Key를 유지했으나 재호출할 때마다 템플릿의 `key`를 새로 만들었다. 서버에 저장된 첫 요청과 재시도 본문이 달라지면 `IDEMPOTENCY_KEY_REUSED`로 거절될 수 있었다.

생성은 기존 공통 `useKeyedOperationIntents`를 사용해 멱등 키와 최초 `{key, name, purpose, body}`를 함께 보존한다. 성공하거나 확정된 4xx 응답을 받으면 해제하고, 네트워크 오류 등 결과가 불확실할 때는 원래 요청을 재사용한다. 다른 입력의 새 생성은 차단하고 화면에서 이전 요청을 명시적으로 다시 시도할 수 있다. 재시도 성공 시 서버가 반환한 용도의 템플릿을 선택한다.

이 보존은 현재 화면의 메모리 범위이며 새로고침·다른 탭까지 이어지지 않는다. 서버 멱등 기록의 보존 기간(24시간)을 확장하는 변경도 아니다.

Web 타입검사·린트·정적 빌드 및 독립 코드 리뷰 통과. 격리 환경의 실제 생성 POST가 201을 반환한 뒤 브라우저에서만 TypeError를 한 번 주입했다. 용도 필터를 바꾼 뒤 이전 요청을 재시도해 두 POST의 본문과 Idempotency-Key 일치, DB 행 수가 정확히 한 건 증가한 상태 유지, 서버 응답 용도로 화면 선택 복귀를 확인했다. 응답 유실은 모의 조건이며 DB 저장·HTTP 처리는 실제 격리 API 결과다.

별도 브라우저 요청에 허용하지 않는 변수를 주입해 실제 서버의 400 응답을 확인한 뒤 정상 생성은 새 멱등 키로 201을 받았다. 이때 미확정 요청 안내가 남지 않았고 DB에는 정상 생성 한 건만 추가됐다. 테스트 파일·스위트는 변경하거나 실행하지 않았다.


## 학생 조회와 응답 매핑 타입

학생 목록과 대표 반 매핑에 남아 있던 `any`를 실제 Prisma `include`·`select`에서 도출한 조회 타입으로 교체했다. 관리자 조회의 연락처 복호화와 공개 검색의 연락처 제외 범위를 타입과 JSDoc으로 연결했다. 공개 배정 조회는 활성 항목만 선택하며, 기존 매핑의 `sourceActive` 검사도 그대로 유지한다.

SQL·필터·정렬·페이지 계산·반 분류를 바꾸지 않았다. TypeScript 설정으로 변환한 JavaScript에서 주석을 제거한 결과는 수정 전과 완전히 같았다. 통합 API 타입검사·빌드와 OpenAPI/Controller 계약 검증을 통과했다. 격리 합성 데이터의 관리자 학생 기본·필터 목록, 검토 필요 목록, 공개 검색 응답은 변경 전후 모두 200이고 JSON이 동일했다.


## 예약 공개·관리자 응답 경계

예약과 학생 연결 매핑의 `any`를 공통 Prisma 조회에서 도출한 타입으로 교체했다. 공개 변경·취소의 마스킹 응답과 연락처를 포함하는 관리자 응답을 구분하고, 멱등 결과를 JSON에서 재생할 때 날짜가 문자열일 수 있음을 관리자 반환 타입에 반영했다.

SQL·권한·트랜잭션·잠금·실제 응답 필드는 유지했다. 주석을 제거한 JavaScript 결과가 수정 전과 같고 통합 API 타입검사·빌드·OpenAPI/Controller 검증을 통과했다. 합성 데이터의 관리자 예약 목록·상세와 공개 본인확인 상세는 변경 전후 모두 200이며 JSON이 같았다. 학생 조회와 합쳐 총 7종 읽기 응답의 완전 일치를 확인했다. 변경·취소 HTTP를 이 단계에서 별도로 실행한 것은 아니며, 타입 검사와 실행 코드 동일성으로 해당 경계를 점검했다. 테스트 코드·스위트는 변경하거나 실행하지 않았다.


## 운영 모듈의 책임과 읽는 순서

실제 HTTP 경계와 정책 처리는 NestJS Controller·구체 Service에, 조회·저장은 Prisma와 SQL에, 외부 통신은 gateway에 둔다. 비동기 작업은 outbox와 worker가 맡는다. 현재 구조를 설명하기 위해 별도의 Service 인터페이스나 단순 전달용 Repository 계층을 추가하지 않았다.

| 영역 | 진입점과 책임 | 코드를 읽을 때 확인할 경계 |
| --- | --- | --- |
| 세미나·회차 | `SeminarsController` → `SeminarsService` | 공개 조회 조건, 관리자 가드·CSRF, 변경의 멱등성·버전 검사, 회차 수정의 행 잠금 |
| 명단·통계 | `SessionRosterService`, `SessionStatisticsService` | 읽기 전용 조회, 대표 예약 선택, 연락처 복호화, XLSX 수식 방어, 예약 기준 예상 인원과 실제 입장의 차이 |
| 입장 | `CheckInsController` → `CheckInsService` | 멱등 키·기기·회차·예약·QR 잠금 순서, HTTP 오류와 입장 결과 코드, 상태·이벤트·outbox의 단일 커밋 |
| 스캐너 | `ScannerDevicesController` → `ScannerDevicesService` | Redis 페어링과 DB의 별도 경계, DB 커밋 이후 세션 저장·무효화, heartbeat 갱신 |
| 학생 동기화 | `StudentSyncOrchestratorService` → `StudentPromotionService` | lease와 로그인 circuit, 외부 조회와 staging, 검증된 원장 승격 트랜잭션, 승격 이후 예약 보정 |
| 문자 관리·발송 | `SmsAdminService` → outbox → `SmsWorkerService` | 미리보기 token 재검증, 전송 전 대기와 전송 중 상태 구분, 결과 불명확 처리와 제한된 재시도 |
| Google Sheets | outbox → `SheetWorkerService` → gateway | 매핑·작업 lease, projection과 외부 적용, 회로 중단·조정 필요 상태와 재시도 |

각 모듈의 Controller 또는 공개 Service 메서드에서 입력·권한·반환 계약을 읽고, 해당 메서드가 호출하는 트랜잭션·매핑·외부 통신 순서로 따라가면 된다. 예약과 학생의 공개 응답 경계는 앞 절의 타입 정리, 문자 편집 허용 변수는 정책 파일을 함께 참고한다.

이 단계는 13개 파일의 한국어 주석을 보완했다. 기존의 “입장 인원이 없으면 아무것도 바꾸지 않는다”는 설명은 예약 상태를 유지하면서 입장 결과 사건은 기록한다는 실제 동작에 맞춰 고쳤다. 총 시도 횟수와 재시도 횟수, 감사 기록 조건, 외부 검증 주기, DB 커밋 뒤 처리도 구분했다.

13개 파일의 TypeScript 변환 결과에서 주석을 제거한 JavaScript가 수정 전과 모두 동일했다. API 타입검사·빌드와 OpenAPI 81경로·96업무 operation 및 Controller 경로 검증을 통과했다. 교차 코드 리뷰로 주석과 실제 분기·SQL을 대조했다. 이 단계에서 입장·동기화·worker의 동작을 새로 실행 검증한 것은 아니다. 테스트 파일·스위트, DB·OpenAPI 계약·의존성·배포 설정은 변경하지 않았다. 실제 문자·학생 원천·Google Sheets 호출이나 AWS 배포도 수행하지 않았다.
