# QR 스캐너 인원 선택 디자인 핸드오프

2인 예약이 게이트에서 QR을 찍었을 때, 실제로 온 학부모가 몇 분인지 현장 스태프가
터치로 고르는 화면. `/scanner/connect` (iPad) 의 스캔 결과 흐름 안에 들어간다.

## 사용자와 핵심 작업

**대상**: 설명회 당일 게이트에 서 있는 운영 스태프. iPad 를 한 손에 들거나 거치대에
세워 두고, 눈앞의 학부모를 보면서 다른 손으로 조작한다. 줄이 밀리는 상황이고, 화면을
읽을 시간은 1초 남짓이다.

**한 가지 목적**: *지금 이 예약으로 몇 분이 들어오시는지* 한 번의 터치로 확정한다.

2인(모/부) 예약인데 실제로는 한 분만 오는 경우가 있어 필요한 화면이다. 1인 예약은
이 화면을 만나지 않고 지금처럼 즉시 입장 처리된다.

## 확정 흐름

```
QR 스캔
  └→ 서버가 QR·회차·예약 상태를 먼저 검증          ← 오류는 여기서 기존 오버레이로 끝난다
       └→ 2인 예약이면 PARTY_SELECTION_REQUIRED    ← 예약은 아직 건드리지 않는다
            └→ [이 화면]  1명 / 2명 선택
                 └→ 선택한 인원으로 입장 확정
                      └→ 기존 CheckInResultOverlay 가 "입장 완료" 로 마무리
```

**이 화면이 뜬 시점에 QR 유효성 검증은 이미 끝나 있다.** 만료·폐기·다른 회차·취소 예약은
여기까지 오지 않고 기존 결과 오버레이가 처리한다. 그래서 이 화면은 오류를 말하지 않고
오직 인원만 묻는다.

**선택 전까지 입장은 확정되지 않는다.** 이것이 이 화면의 가장 중요한 성질이자
가장 큰 위험이다 — 스태프가 선택을 놓치면 그 가족은 입장 처리가 안 된 채 남는다.
디자인은 이 위험을 상쇄하는 데 예산을 써야 한다.

## 기존 패턴과 새 패턴

**그대로 승계하는 것**

| 요소 | 출처 |
| --- | --- |
| 전체 화면 어두운 면 `#0A0F1A`, `position: fixed; inset: 0` | `ScannerConnectView` |
| 결과 프레임 — `--radius-lg`, 1px 톤 보더, 톤 10% 배경, 가운데 정렬 | `CheckInResultPanel` |
| 어두운 배경 전용 상태색 `--status-*-on-dark` | 같은 파일 |
| 아이콘(lucide) + 문구를 **항상 함께** — 색만으로 뜻을 전달하지 않는다 | 핸드오프 요구 |
| `role="alertdialog"` + `aria-modal="true"` 오버레이 | `CheckInResultOverlay` |
| 대표학생 표기 `{이름} 학생 학부모(모/부)` | `check-in-copy.ts` |
| 해요체, 시스템 용어 없음 | 전 화면 공통 |

**새로 생기는 패턴 — 답해야 닫히는 오버레이**

이 앱의 모든 오버레이는 지금까지 **알려 주고 3초 뒤 스스로 사라졌다**. 스태프는 이미
"오버레이는 기다리면 없어진다"를 학습했다. 이 화면이 그 오버레이와 비슷해 보이면
스태프는 기다릴 것이고, 그 가족은 입장 처리가 되지 않는다.

따라서 **자동 닫힘 타이머를 두지 않는다**는 것만으로는 부족하고, 화면 스스로
"이건 네가 눌러야 넘어간다"를 형태로 말해야 한다. 세 시각안은 그 신호를 서로 다른
방식으로 싣는다.

## 정보 위계

1. **누구인가** — `{대표학생명} 학생 학부모(모/부)`. 스태프가 눈앞의 사람과 대조하는 단서다.
   이름이 없으면(계약상 방어) 이 줄을 지어내지 말고 `2명 예약` 만 남긴다.
2. **질문** — 몇 분 입장하세요?
3. **두 개의 선택** — 1명 / 2명. 화면에서 가장 큰 요소이며 서로 대등하다.
   기본 선택(권장값)을 두지 않는다 — 어느 쪽도 더 흔하다고 가정할 근거가 없고,
   기본값은 스태프가 확인 없이 누르게 만든다.
4. **미확정 신호** — 아직 입장 처리 전이라는 사실.
5. **탈출구** — 취소하고 다시 스캔. 작고 조용하게, 그러나 도달 가능하게.

숫자(1·2)는 글자보다 크게 — 게이트에서 흘긋 보고 누르는 동작이 문장 읽기보다 빠르다.

## 인터페이스 문구

| 자리 | 문구 |
| --- | --- |
| 제목 | `몇 분 입장하세요?` |
| 예약 요약 | `{이름} 학생 학부모(모/부) · 2명 예약` |
| 선택 A | `1명` / 보조: `한 분만 입장` |
| 선택 B | `2명` / 보조: `두 분 모두 입장` |
| 미확정 배지 | `아직 입장 처리 전이에요` |
| 탈출 | `취소하고 다시 스캔` |
| 처리 중 | `입장 처리 중…` |
| 실패 | `입장 처리를 못 했어요. 같은 QR을 다시 스캔해 주세요.` |
| 취소 후 토스트 | `입장 처리하지 않았어요. 다시 스캔하면 이어서 할 수 있어요.` |

"확인", "제출", "선택" 같은 시스템 동사를 쓰지 않는다. 버튼이 말하는 그대로가
일어나는 일이어야 한다 — `1명` 을 누르면 1명이 입장한다.

## 상태

| 상태 | 화면 |
| --- | --- |
| **선택 대기** (기본) | 두 선택지 활성. 타이머 없음. |
| **처리 중** | 누른 쪽에 인라인 스피너, **양쪽 모두 비활성**. 이중 확정을 막는다. 문구는 `입장 처리 중…`. |
| **성공** | 이 화면은 닫히고 기존 `CheckInResultOverlay` 가 `… 1명 입장 완료` 로 마무리한다. **새 성공 화면을 만들지 않는다.** |
| **실패** | 이 화면을 닫고 기존 오류 패널로 넘긴다. 스태프가 할 일(같은 QR 재스캔)을 말한다. |
| **취소** | 카메라로 복귀 + 중립 토스트. 예약은 그대로 미입장. |
| **세션 상실** | 하트비트가 세션 상실을 알리면 이 화면을 즉시 닫고 기존 페어링 흐름을 따른다. 선택을 붙들지 않는다. |

빈 상태·로딩 상태는 없다 — 이 화면은 서버가 예약 정보를 이미 준 뒤에만 열린다.

## 접근성과 키보드

- `role="alertdialog"` — 답을 요구하는 대화 상자다. `aria-modal="true"`.
- `aria-labelledby` → 제목, `aria-describedby` → 예약 요약.
- 열릴 때 포커스를 대화 상자로 옮기고 **포커스를 가둔다**. 닫히면 카메라 영역으로 되돌린다.
- **자동 닫힘 없음.** 시간으로 사라지는 경로를 두지 않는다.
- `Escape` → `취소하고 다시 스캔` 과 같은 동작. 결과(입장 처리 안 됨)를 토스트로 말한다.
- 두 선택지는 진짜 `<button>`. 최소 터치 타깃 **88×88px** — iPad 게이트에서 장갑·급한 손을
  전제로 44px 최소치의 두 배로 잡는다.
- 숫자만으로 구분하지 않는다: 각 선택지는 숫자 + 문장 + 아이콘을 함께 싣는다.
- `처리 중` 전환은 `aria-live="polite"` 로 알린다. 결과 낭독은 기존 결과 패널이 이미 담당하므로 중복하지 않는다.
- `prefers-reduced-motion` 존중 — 등장 애니메이션은 투명도만 남긴다.

## 반응형

`/scanner/connect` 는 iPad 우선이지만 같은 컴포넌트가 폰에서도 열릴 수 있다.

- **≥768px (iPad 세로·가로)**: 두 선택지를 가로로 나란히, 각 최소 높이 200px.
  가로 모드에서도 두 선택지가 접히지 않게 한다.
- **<768px**: 세로로 쌓고 각 최소 높이 120px, 폭은 가득. 예약 요약은 두 줄까지 허용.
- 어느 폭에서도 선택지가 화면 밖으로 나가거나 스크롤을 요구하지 않는다 —
  스크롤해야 보이는 선택지는 놓치는 선택지다.

**새로 만들 것**: 인원 선택지 두 장과 그것을 담는 오버레이 하나뿐.

## ★ 제품 언어: 좌석 개념은 없다

이 제품에 **좌석(seat)이라는 개념은 존재하지 않는다.** 세는 단위는 오직 **사람 수(명)** 다.

- 화면·문구·계약 필드 어디에도 `좌석`/`seat`/`자리`를 쓰지 않는다.
- 좌석 한도, 잔여 좌석, 좌석 기반 비율은 제품 범위가 아니다
  (`apps/web/README.md` 제품 표시 불변식).
- DB 의 `family_bookings.seat_count` 와 계약의 `familySeatCount` 는 **기존 내부 명명**이며
  화면에는 언제나 `N명` 으로만 나타난다. 이번에 추가하는 값은 좌석 어휘를 승계하지 않고
  참석 인원 어휘(`attendedCount`)를 쓴다.

## 시각안 — **1번 확정** (2026-08-16)

세 안의 차이는 장식이 아니라 **"눌러야 넘어간다"는 신호를 무엇이 지느냐**였다.
사용자가 **1번(정면 질문)** 을 선택했다. 나머지 두 안은 기록으로만 남긴다.

### ★ 1. 정면 질문 — 선택됨

기존 결과 오버레이의 연장선. 짙은 스크림 위에 질문 한 줄, 예약 요약 한 줄, 그리고
동일한 크기의 카드 두 장. 신호는 **타이머의 부재 + 미확정 배지**가 진다.

가장 안전하고 학습 비용이 낮다. 대신 기존 오버레이와 닮은 만큼 "기다리면 사라지겠지"
오해의 여지가 가장 크므로, **미확정 배지가 눈에 확실히 들어와야 한다** — 이 안에서
디자인 예산을 가장 많이 써야 하는 지점이다.

구현 지침:
- 카드 두 장은 정확히 같은 크기·같은 시각 비중. 어느 쪽도 primary 로 강조하지 않는다.
- 숫자(`1` / `2`)를 `--font-display` 로 크게, 보조 문장은 그 아래 작게.
- 미확정 배지는 `--status-warning-on-dark` 로 카드 **위**(질문 바로 아래)에 둔다 —
  하단은 시선이 마지막에 닿는 자리라 놓치기 쉽다.
- 배경 스크림은 기존 결과 오버레이보다 짙게 해서 "다른 종류의 오버레이"임을 만든다.

### 2. (기록) 분할 게이트

화면을 세로로 반으로 갈라 좌우 전체가 각각 선택지. 터치 타깃이 압도적이지만
다른 화면과 가장 이질적이라 이 화면만 튀어 보인다. 미채택.

### 3. (기록) 폐기된 안

세 번째 안은 예약 인원을 좌석 은유로 그리는 방향이었으나, 이 제품에 좌석 개념이
없으므로 **제품 언어 위반**이다. 폐기.

**공통 금지**: 좌석 어휘, 기본 선택값, 3초 자동 닫힘, 색만으로 구분되는 선택지,
스크롤해야 보이는 선택지, 성공 화면 중복 제작.
